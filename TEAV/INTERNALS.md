# TEAV — Внутреннее устройство

Документ описывает архитектуру приложения, причины принятых решений
и проблемы, возникшие в ходе разработки.

---

## Общая архитектура

```
Program.cs                        ← CLI, ввод/вывод, промпт действий
│
├── Core/Scanner.cs               ← оркестратор: запускает 3 этапа
│   ├── Modules/SignatureScanner  ← этап 1: сигнатуры
│   ├── Modules/StaticAnalyzer   ← этап 2: статика
│   │   └── Modules/PeParser     ← самописный PE-парсер
│   └── Modules/HeuristicEngine  ← этап 3: эвристика
│
├── Core/ScanResult.cs            ← общий объект результата
└── Core/Quarantine.cs            ← изоляция угроз
```

Поток данных намеренно однонаправленный: каждый модуль получает данные
и возвращает результат, не зная о существовании других модулей.
`Scanner` — единственная точка сборки.

---

## Модуль 1 — Сигнатурный анализ (`SignatureScanner.cs`)

### Что делает
Загружает базу хэшей `vvv.txt` в `HashSet<string>`, вычисляет MD5, SHA1
и SHA256 проверяемого файла, ищет совпадение.

### Почему HashSet
При миллионе+ записей в базе поиск должен быть O(1).
`List` дал бы O(n) на каждый файл — при 3000 файлов выборки
это 3 миллиарда сравнений. `HashSet` сводит это к ~3 вычислениям хэша строки.

### Почему три алгоритма хэширования
Разные базы данных малвари используют разные алгоритмы (VirusShare — MD5,
MalwareBazaar — SHA256). Поддержка всех трёх за один проход по файлу
не увеличивает время I/O: буфер читается один раз, три объекта
`HashAlgorithm.TransformBlock()` обновляются параллельно.

### Ранняя остановка
Если сигнатура найдена, `Scanner` немедленно возвращает результат,
не запуская статический и эвристический анализ. Сигнатура — факт,
дополнительный анализ избыточен.

## Модуль 2 — Парсер PE-файлов (`PeParser.cs`)

### Почему самописный, а не библиотека
PE-формат хорошо специфицирован (MSDN: IMAGE_NT_HEADERS).
Написать необходимое подмножество (~250 строк) дешевле, чем тащить
библиотеку ради чтения заголовков. Заодно это демонстрирует
понимание формата.

### Что парсится

**DOS-заголовок** — проверка сигнатуры `MZ` (0x5A4D) и чтение
смещения PE-заголовка из поля `e_lfanew` (offset 0x3C).

**PE-сигнатура** — 4 байта `PE\0\0` (0x00004550).

**COFF-заголовок** — количество секций, размер Optional Header.

**Optional Header** — здесь ключевой момент: для PE32 и PE32+ (64-бит)
структура различается. Поле `ImageBase` имеет разный размер (4 vs 8 байт),
`BaseOfData` присутствует только в PE32. Из-за этого смещение
до массива `DataDirectory` разное:
- PE32:  96 байт от начала Optional Header
- PE32+: 112 байт от начала Optional Header

Эти смещения вычислены по спецификации и проверены вручную на тестовых EXE.

**Таблица секций** — для каждой секции парсятся имя, виртуальный адрес,
сырое смещение/размер и флаги (исполняемая, записываемая).
По сырым данным секции немедленно вычисляется энтропия Шеннона.

**Таблица импортов (IAT)** — каждый `IMAGE_IMPORT_DESCRIPTOR` (20 байт)
содержит RVA имени DLL и RVA массива Thunk. Thunk-записи для PE32
занимают 4 байта, для PE32+ — 8. Старший бит записи означает импорт
по ординалу; иначе RVA указывает на `IMAGE_IMPORT_BY_NAME`
(2-байтовый hint + null-terminated имя функции).

**TLS Directory** — проверяется наличие ненулевого RVA в `DataDirectory[9]`.
Ненулевой RVA означает, что в файле есть TLS-колбэки — код, исполняемый
до `AddressOfEntryPoint`, что является классической техникой обхода отладчиков.

### RVA → файловое смещение
Виртуальный адрес в PE не совпадает с позицией в файле (разные выравнивания).
Перевод: находим секцию, в диапазон которой попадает RVA, и вычитаем
разницу между виртуальным адресом секции и её сырым смещением.

## Модуль 3 — Статический анализатор (`StaticAnalyzer.cs`)

### Цифровая подпись через WinVerifyTrust
Windows предоставляет API `WinVerifyTrust` из `wintrust.dll` для проверки
подписи Authenticode. Использован P/Invoke — прямой вызов нативной функции
из управляемого кода без дополнительных зависимостей.

Код возврата `0x800B0100` (`TRUST_E_NOSIGNATURE`) означает отсутствие подписи.
`0` — подпись валидна. Любой другой код — подпись есть, но недоверенная
(отозвана, истекла и т.д.).

### Обнаружение упаковщиков
Двухэтапное: сначала сравниваем имена секций (`UPX0`, `MPRESS1` и др.),
затем ищем байтовые маркеры в первых 512 KB файла алгоритмом
Boyer-Moore-Horspool (O(n/m) в среднем vs O(n·m) у наивного поиска).

### Извлечение строк
Извлекаются как ASCII-строки (однобайтовые символы 0x20–0x7E длиной ≥ 5),
так и UTF-16LE строки (двухбайтовые, характерны для нативных Windows-приложений).
Оба потока конкатенируются и проверяются regex-паттернами.

### Скрытые импорты
Если файл использует `GetProcAddress` + `LoadLibraryA` — он разрешает
API-функции в рантайме, не объявляя их в IAT. Это стандартная техника
сокрытия подозрительных импортов от статического анализа.
Флаг `HiddenImports` передаётся в эвристику.

## Модуль 4 — Эвристический движок (`HeuristicEngine.cs`)

### Система баллов

| Условие | Баллы |
|---------|-------|
| Файл не подписан | +20 |
| Высокая энтропия (> 6.5) исполняемой секции | +25 |
| WriteProcessMemory + CreateRemoteThread вместе | +30 |
| PowerShell encoded команды (-enc) | +20 |
| Ключ автозапуска в реестре | +15 |
| reg add / schtasks (системная персистентность) | +40 |
| Обнаружен упаковщик | +30 |
| Скрытые импорты | +25 |
| TLS-колбэки | +20 |
| Прочие подозрительные API (по таблице) | индивидуально |

**Порог 70** → Suspicious  
**Порог 100** → Malicious

### Защита от двойного счёта
API `WriteProcessMemory` и `CreateRemoteThread` при совместном
обнаружении дают комбо-бонус +30. Чтобы они не дали ещё и
индивидуальные баллы, используется `HashSet<string> counted` —
после применения комбо-правила оба имени маркируются как учтённые
и пропускаются в цикле по отдельным API.

Аналогично для строковых паттернов: строки, уже учтённые в
специфических правилах (PowerShell, reg add и т.д.), исключены
из общего прохода через `alreadyCounted`.

## Карантин (`Quarantine.cs`)

Файл XOR-шифруется байтом `0xAA` и сохраняется с расширением `.quar`.
Это не криптографическая защита — цель в том, чтобы файл нельзя было
случайно запустить и чтобы антивирус самой системы не срабатывал
на файл в карантине снова.

XOR симметричен (операция тождественна для шифрования и расшифровки),
что упрощает функцию восстановления.

Рядом с `.quar` создаётся `.meta` — JSON с исходным путём, хэшами,
причиной детекции, датой. Это позволяет восстановить файл или
изучить его позже.

## Проблемы при разработке и их решение

### 1. `yield return` внутри `catch` — ошибка компилятора CS1631
C# не допускает `yield return` внутри блока `catch` в методах-генераторах.

**Решение:** исключение перехватывается отдельно, результат ошибки
записывается в локальную переменную `dirError`, а `yield return`
вызывается уже за пределами `catch`.

### 2. `dynamic` без пакета `Microsoft.CSharp` — ошибка CS0656
`Newtonsoft.Json` возвращает `dynamic` при десериализации без типа,
но сам биндинг `dynamic` требует пакет `Microsoft.CSharp`, который
в SDK-style проектах на .NET Framework не подключается автоматически.

**Решение:** создан конкретный класс `QuarantineMeta` с нужными полями,
десериализация выполняется в него — `dynamic` не нужен.

### 3. Разные смещения DataDirectory для PE32 и PE32+
Optional Header у 32- и 64-битных PE-файлов различается по структуре.
Из-за этого массив `DataDirectory` (Import, TLS и др.) начинается
на разных байтовых смещениях (96 vs 112).

**Решение:** `magic`-поле Optional Header (`0x010B` vs `0x020B`) читается
первым, после чего выбирается нужная константа смещения. Значения
96 и 112 получены из официальной спецификации PE (MSDN: Optional Header).

### 4. Размер Thunk-записи в таблице импортов
Аналогично предыдущему: в PE32 каждая запись в Thunk-массиве занимает
4 байта, в PE32+ — 8. Признак ординального импорта — старший бит
(бит 31 для PE32, бит 63 для PE32+).

**Решение:** вся логика чтения Thunk параметризована флагом `is64`,
который определяется из `magic`.

### 5. RvaToOffset и внутренний тип секции
Публичный тип `SectionEntry` (передаётся наружу) не хранит `VirtualAddress`
(вызывающему коду он не нужен). Но для перевода RVA в файловое смещение
он необходим. Если бы парсер использовал `SectionEntry` внутренне,
поле либо пришлось бы сделать публичным без нужды, либо метод
`RvaToOffset` не смог бы работать.

**Решение:** введён внутренний тип `RawSection` с полным набором полей.
После парсинга данные копируются в `SectionEntry` для публичного API.
Таким образом, публичный контракт остаётся чистым.
